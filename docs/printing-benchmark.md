# Print timing instrumentation and benchmark protocol

This document describes the per-ticket timing trace built into ePOS Proxy and
the protocol used to measure printing on macOS with an Epson receipt printer and
Odoo 19.

The goal is **observation only**. Nothing here defines an improvement target, a
preferred image mode, or a claim that one mode is faster. Thresholds are set by
whoever runs the benchmark, after the baseline exists.

Related work that this document does **not** replace:

- Physical baseline on real hardware (separate task).
- Firefox compatibility diagnosis (separate task).
- CUPS as an opt-in mode (`feat/cups-driver-receipts-*`, not merged). This
  document reserves the CUPS fields; on `main` they are always `-`.

## 1. Where the trace lives

| Stage | File | What it measures |
|---|---|---|
| Ticket correlation and log line | `internal/trace/trace.go` | request id, field rendering, sanitising |
| Server stages | `internal/server/server.go` (`printData`, `printLabel`) | body read, XML parse, queue hand-off, total |
| Printer stages | `internal/printer/printer.go` (`write`), `internal/printer/manager.go` (`WriteAsyncTraced`) | open, write blocks, bytes, close |

The trace is passive: it records what the existing code already does and never
changes the ESC/POS bytes, the order of device operations, or the ePOS response.
`TestPrintData_DeviceBytesMatchEscposOutput` and
`TestWriteTracedKeepsDeviceBytesIdentical` enforce that guarantee.

The line is emitted from a goroutine after the response is written, because
`net/http` may buffer a small response until the handler returns. The
`request_id` response header is set before any printing starts, so a client can
read it as soon as the response arrives. Consequence: a `print_trace` line may
appear in the log *after* the matching `Proxy request` line, and up to
`SettleTimeout` (250 ms) later if the device close is slow. Correlate by
`request_id`, not by line order.

### Log file

One `print_trace` line is written per ticket at `info` level, so it is enabled in
release builds (no debug flag required):

| OS | Path |
|---|---|
| macOS | `~/Library/Application Support/EposProxy/logs/epos-proxy.log` |
| Linux | `~/.config/EposProxy/logs/epos-proxy.log` |
| Windows | `%AppData%\EposProxy\logs\epos-proxy.log` |

Logs rotate at 20 MB with 5 backups, so a 20 × 3-ticket benchmark fits easily,
but copy the log out before running a second batch.

Only `POST .../cgi-bin/epos/service.cgi` and `POST .../pstprnt` produce a trace
line. CORS preflights, health checks, rejected requests (403 for remote clients
when network printing is off) and malformed HTTP never reach the print handler:
their absence is a signal by itself.

### Example line

```text
print_trace request_id=9f2c0c1aa1b4d3e5 kind=receipt printer_id=bDoxMjcuMC4wLjE transport=lan image_mode=legacy status=ok code=- xml_bytes=146432 escpos_bytes=150112 device_bytes=150112 write_blocks=1 image_count=1 raster_w=576 raster_h=4096 recv_at=2026-11-15T08:12:41.882113Z body_ms=0.412 parse_ms=8.113 enqueue_ms=0.051 open_ms=0.004 open_reused=true write_ms=30.221 block_ms=30.221 close_ms=0.010 close_done=true cups_lp_ms=- cups_drain_ms=- total_ms=39.207
```

### Fields

Unknown or not-applicable values are always the single token `-`, never an
empty value, so every field is present in every line.

| Field | Unit | Meaning |
|---|---|---|
| `request_id` | token | Per-ticket correlation id (see below) |
| `kind` | `receipt` / `label` | Which endpoint handled the request |
| `printer_id` | token | Printer id used by Odoo (USB id or encoded LAN id) |
| `transport` | `usb` / `lan` / `cups` | Transport implied by the printer id (`cups` only on the CUPS build) |
| `image_mode` | `none` / `legacy` / `gs_l` / `raw` | Raster command found in the generated bytes: `none` = no image, `legacy` = `GS v 0`, `gs_l` = Epson `GS ( L`, `raw` = label bytes forwarded verbatim |
| `status` | `ok` / `error` | Outcome reported to Odoo |
| `code` | ePOS code | `EX_BADPORT`, `TooManyRequests`, `SchemaError`, `BadRequest`, `PayloadTooLarge`, `EmptyLabel`, or `-` |
| `xml_bytes` | bytes | Request body size |
| `escpos_bytes` | bytes | Generated ESC/POS size |
| `device_bytes` | bytes | Bytes the device accepted (equals `escpos_bytes` unless the write failed part-way) |
| `write_blocks` | count | Number of physical writes (`GS v 0` tickets over USB are chunked; LAN is a single block on `main`) |
| `image_count` | count | Number of `<image>` elements in the ticket |
| `raster_w` | dots | Widest image |
| `raster_h` | dots | Sum of image heights |
| `recv_at` | RFC 3339 | Handler entry time (UTC), for correlating with video/client logs |
| `body_ms` | ms | Reading and size-limiting the body |
| `parse_ms` | ms | ePOS XML → ESC/POS |
| `enqueue_ms` | ms | From handing the job to the printer queue until the printer loop starts it (includes waiting behind earlier tickets) |
| `open_ms` | ms | USB enumeration/claim or TCP connect performed by the write path |
| `open_reused` | bool | `true` when the connection was already open, i.e. no reconnect for this ticket |
| `write_ms` | ms | Whole device write |
| `block_ms` | ms list | Duration of each block, comma separated, in write order |
| `close_ms` | ms | Time spent closing the device for this ticket |
| `close_done` | bool | `true` when the close happened at the end of this ticket; `false` when the device stayed open because more tickets were queued |
| `cups_lp_ms` | ms | Reserved: `lp` submission time (CUPS build only) |
| `cups_drain_ms` | ms | Reserved: time until the job leaves `lpstat -o <queue>` (CUPS build only) |
| `total_ms` | ms | Handler entry → ePOS response serialised. Includes queueing, open, write and trace bookkeeping, excludes the post-response close wait |
| `error` | quoted string | Present only on failure; newlines are folded to spaces |

Stage boundaries are disjoint except for `total_ms`, which contains all of them.
Two costs are deliberately outside the per-stage timers and only visible in
`total_ms`:

1. Trace bookkeeping: scanning the body for `<image>` tags and the generated
   stream for the raster command. This is two short memory scans (no XML parse,
   no base64 decode) and stays well below 1 ms for a 150 KB ticket.
2. Device discovery for a **new** printer id: `Manager.Get` opens the device
   before the job is queued, so it is not part of `open_ms`. It happens once per
   printer id per process; the cold-start scenario in §3 measures it.

### Correlating a ticket

`request_id` is generated per ticket and returned to the client in the
`X-Request-Id` response header (visible in the browser network tab; not exposed
to page JavaScript). A client that already has an id can send
`X-Request-Id` on the request; it is kept when it is a safe token (up to 64
characters of `A-Z a-z 0-9 - _ . :`), otherwise it is replaced, so the value can
never break the log line.

The benchmark loop in §3 sets `X-Request-Id` to a scenario-prefixed token; that
single value links the client-side measurement, the browser network tab, the
`Proxy request` log line and the `print_trace` line.

### Privacy

The line contains identifiers and sizes, never receipt content, credentials or
customer data. Text is not logged; `error` carries only the Go error string.
Printer ids are the same identifiers the app already shows in its UI.

## 2. What the trace cannot tell you

- **Primer papel / corte**: the proxy cannot see paper. Those two must be filmed
  or timed by a person (§3.5).
- **CUPS end-to-end**: on `main` nothing goes through CUPS. `cups_lp_ms` and
  `cups_drain_ms` stay `-` until the CUPS build is validated; even then, "job
  left the queue" is not "paper cut".
- **Duplicados**: the proxy sees each request once. A duplicate caused by the
  operator pressing print again is a new ticket with a new `request_id`; only
  counting physical receipts reveals it.
- **Browser-side rendering**: `xml_bytes` and `raster_h` tell you whether
  Firefox and Chrome produced the same ticket, not why.
- **Transport on a CUPS build**: `transport` is derived from the printer id and
  on `main` only distinguishes USB from LAN. DS-9 (PR #4) **must** report an
  explicit `cups` value (`trace.TransportCUPS`) for tickets submitted through
  CUPS before merging; reusing `lan` is not allowed because it would mix CUPS
  and direct-LAN samples in the same benchmark scenario while
  `cups_lp_ms`/`cups_drain_ms` are set.

## 3. Benchmark protocol

The protocol must be reproducible by someone who has never run it. Record every
value below before starting; a report without them cannot be compared with
anything.

### 3.1 Equipment and versions

```
Printer model:
Printer firmware (self-test page):
Connection: USB | LAN (IP)
Mac model + chip: (Intel | Apple Silicon)
macOS version:
Odoo version: (19.0 | 19.1) and scheme: (http | https)
point_of_sale.use_lna:
Browser + version:
Proxy build: commit sha + mode build (main | PR #3 | PR #4)
Printer address used in Odoo:
Paper width (58 | 80 mm) and quality:
```

### 3.2 Tickets

Three fixed ticket bodies, frozen as files before measuring (`ticket-short.xml`,
`ticket-medium.xml`, `ticket-long.xml`) and identified by SHA-256. The bodies
must be the ones Odoo itself produces: open the browser devtools, print in the
POS, save the request body of `service.cgi`, and replay it with the loop in
§3.4. This keeps Odoo's exact raster (dithering, margins) without hand-crafting
base64.

| Ticket | Content | Expected shape |
|---|---|---|
| `short` | Text only, ~20 lines, cut | few hundred bytes of ESC/POS, no image |
| `medium` | Text + QR or barcode as image, ~20–25 cm, cut | `image_count≥1`, `raster_h` in the low thousands |
| `long` | Text + large graphics, printed length **> 297 mm**, cut | `raster_h` clearly above ~2300 dots at 203 dpi; verify the last line and the cut |

Rules:

- The long ticket must exceed 297 mm physically; measure the paper with a ruler
  and record it.
- Mark the last line of every ticket (for example `END-t3`) so a truncated
  receipt is visible.
- Record `xml_bytes`, `escpos_bytes`, `image_count`, `raster_w`, `raster_h` from
  the first trace line of each scenario and confirm they stay constant across
  repetitions. A changing `xml_bytes` means the ticket is not frozen.

### 3.3 Modes and scenarios

| Mode | Build | Condition |
|---|---|---|
| `legacy` | `main` | USB or LAN, `GS v 0` raster |
| `gs_l` | PR #3 build | LAN with a model that supports Epson graphics |
| `cups` | PR #4 build | LAN with an Epson queue already installed and authorised |

Each mode is measured only where it exists; do not compare a USB `legacy` run
with a LAN `cups` run.

Scenario id = `<ticket>-<mode>-<start>-<nn>`, for example
`t3-gsl-cold-07`. Use it as `X-Request-Id` so every line is filterable.

| Factor | Values |
|---|---|
| Ticket | `t1`, `t2`, `t3` |
| Mode | `legacy`, `gs_l`, `cups` (when available) |
| Start | `cold`, `warm` |
| Repetitions | 20 per scenario |

**Cold**: quit the app completely (`App → Quit`), start it, and print exactly one
ticket. Repeat 20 times. This captures device discovery, first open and the
USB driver claim.

**Warm**: start the app, print 5 tickets that are not measured, then print 20.
This is the state a shop is in during the day.

Do not mix `cold` and `warm` lines in the same percentile set.

### 3.4 Running the repetitions

Set the address to the one shown by the app (no `http://` prefix in Odoo; for
`curl` use the full URL). `PRINTER_ID` is the printer id from the app, `PORT` the
listening port.

```sh
PRINTER_ID='<printer id from the app>'
BASE="http://127.0.0.1:${PORT}/p/${PRINTER_ID}/cgi-bin/epos/service.cgi"

for i in $(seq -w 1 20); do
  curl -sS -o /dev/null \
    -H 'Content-Type: text/xml' \
    -H "X-Request-Id: t1-legacy-warm-${i}" \
    --data-binary @ticket-short.xml \
    "$BASE"
  sleep 3
done
```

Notes:

- `sleep 3` gives the printer time to finish before the next ticket. Do not
  shorten it for `legacy`; for `long` raise it to at least 10 s.
- `curl` measures the HTTP response, not paper. The response is what Odoo waits
  for; the device stages are in the trace line.
- If you print from Odoo instead of `curl`, still set the request id: the Odoo
  path does not let you, so use the generated id and correlate by `recv_at`.
- Run scenarios in an interleaved order (one round of each mode, then repeat) to
  spread drift (temperature, paper roll tension, Mac thermal state).
- Never change firmware, paper, printer model, macOS or Odoo in the middle of a
  batch.

### 3.5 Measuring first paper and cut

The proxy cannot observe paper. For every repetition, film the printer at 60 fps
with the screen in frame, or use two stopwatches.

1. Start recording.
2. Trigger the ticket (press print in Odoo / run `curl`).
3. Stop after the cut.

From the video, count frames for:

- **first paper**: trigger → first visible paper edge;
- **cut**: trigger → cutter bar movement / separation.

Record both, plus the trace `recv_at`, so the three numbers (HTTP response, first
paper, cut) can be aligned. A ticket that answers in 40 ms and cuts after 2 s is
a firmware/transport problem, not a proxy problem; that is exactly the
distinction this protocol exists to make.

If video is not possible, record a stopwatch measurement and mark the report as
`±150 ms` precision.

### 3.6 Duplicates and failures

- Count printed receipts and compare with tickets sent. Any extra receipt is a
  duplicate: record ticket, mode, and whether Odoo showed a timeout/retry.
- Record every `status=error` line with its `code` and `error` value.
- Record any `request_id` that produced two receipts.
- Do not remove failed runs from the sample; report `n` and the failure count.

## 4. Metrics and report

For each scenario compute, over the 20 repetitions:

| Metric | Source |
|---|---|
| HTTP response (`total_ms`) | trace |
| body / parse / enqueue / open / write / close | trace |
| first paper, cut | video (§3.5) |
| errors, error codes | trace `status`, `code` |
| duplicates | physical count |
| `xml_bytes`, `escpos_bytes`, `device_bytes`, `write_blocks`, `raster_w`, `raster_h` | trace |
| p50, p95, min, max | computed, nearest-rank, `n` = successful samples |

Percentiles use the nearest-rank method on the ordered sample:
`p50 = value at ceil(0.50 × n)`, `p95 = value at ceil(0.95 × n)`. With `n = 20`,
`p95` is the 19th value — report `n` next to it and never present `p95` from
fewer than 20 samples as a stable number.

### 4.1 Extracting a scenario from the log

```sh
LOG="$HOME/Library/Application Support/EposProxy/logs/epos-proxy.log"
grep 'print_trace' "$LOG" | grep 'request_id=t1-legacy-warm-' > t1-legacy-warm.log
```

The logger wraps the message in double quotes (`msg="print_trace …"`); the
values are still space separated, so filtering by `print_trace` or by any
`key=value` works unchanged.

### 4.2 Summary snippet

`awk` is available on stock macOS. Set `key` to any duration field
(`total_ms`, `write_ms`, `parse_ms`, `open_ms`, …) and `prefix` to the scenario
id prefix. Failed tickets are counted as `errors` and excluded from the
percentiles:

```sh
awk -v key=total_ms -v prefix=t1-legacy-warm- '
{
  id = ""; val = ""; st = ""
  for (i = 1; i <= NF; i++) {
    if ($i ~ /^request_id=/) id = substr($i, 12)
    if ($i ~ /^status=/)     st = substr($i, 8)
    if (index($i, key "=") == 1) val = substr($i, length(key) + 2)
  }
  if (prefix != "" && index(id, prefix) != 1) next
  total++
  if (st == "error") { errors++; next }
  if (val == "" || val == "-") { missing++; next }
  n++; v[n] = val + 0
}
END {
  if (n == 0) { printf "%s: no samples (lines=%d, errors=%d, missing=%d)\n", key, total, errors, missing; exit }
  for (i = 1; i <= n; i++)
    for (j = i + 1; j <= n; j++)
      if (v[j] < v[i]) { t = v[i]; v[i] = v[j]; v[j] = t }
  p50 = v[int((n * 50 + 99) / 100)]
  p95 = v[int((n * 95 + 99) / 100)]
  printf "%s n=%d errors=%d missing=%d min=%.3f p50=%.3f p95=%.3f max=%.3f\n", key, n, errors, missing, v[1], p50, p95, v[n]
}
' t1-legacy-warm.log
```

Run it once per field. Same input, different `key`, no re-filtering needed.

```text
total_ms n=3 errors=1 missing=0 min=39.207 p50=41.000 p95=43.100 max=43.100
write_ms n=3 errors=1 missing=0 min=30.221 p50=31.000 p95=32.500 max=32.500
```

## 5. Interpreting (without over-claiming)

- `total_ms` high, `write_ms` low, paper slow → the time is not in the proxy or
  the network; look at how the firmware interprets the raster (this is the
  hypothesis to test with modes, not a conclusion).
- `write_ms` high, `block_ms` growing → device backpressure; compare block sizes
  and transports.
- `open_ms` high on `cold` only → device discovery cost; on `warm` it points at
  close/reopen per ticket.
- `enqueue_ms` high → tickets are waiting behind each other; check for a stuck
  job before blaming the printer.
- `parse_ms` high → XML is large or the image is huge; compare `xml_bytes` and
  `raster_h` between browsers.
- A long ticket that reaches the cut but misses its last lines is a media/length
  problem, not a timing problem.

No conclusion about speed is valid without at least the three tickets, both
start states and the physical measurements. Anything less is an anecdote.
